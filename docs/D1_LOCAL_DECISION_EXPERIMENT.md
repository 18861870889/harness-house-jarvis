# D1 本地决策实验

本文描述初始 v1 HTTP/网页实验，以下结果为历史基线。后续 [Pi 稳定性加固](PI_HARNESS_HARDENING.md) 和 [意图/上下文 v2](D1_INTENT_CONTEXT_V2.md) 在独立 SDK 运行时完成；尚未切换本页的 `demo:d1` 或主网页。当前验证结果请看 v2 文档，不要把旧基线当作当前全部功能。

## 定位

验证局域网 D1 能否以免费、低延迟的方式承担设备决策。不增加独立的复杂规划器，也不回退到 DeepSeek 或其他云端模型。实验基于 Jarvis 仓库已提交的 `353b0ed`，在独立分支开发；不包含本机尚未提交的 Jarvis 变更，不覆盖原来的运行配置、户型或设备映射。

D1 是有限选项决策模型，不是自由生成聊天或任意 JSON 计划的模型。候选计划必须存在，模型才能选择。官方依据：[模型说明](https://docs.liquid.ai/lfm/models/decision-models)、[使用指南](https://docs.liquid.ai/guides/decision-model-guide)、[模型卡](https://huggingface.co/LiquidAI/d1-3B)。能力分类沿用现有 HCM，并参考 [Home Assistant intents](https://developers.home-assistant.io/docs/intent_builtin/)；没有额外引入语法引擎或规划框架。

## 链路

```text
用户指令 + 当前 HCM + 有效会话焦点
  -> 从设备名称、别名、逻辑房间、能力生成有界候选
  -> D1 /v1/systemone 选择方案与读写目的（一次请求，独立问题）
  -> 严格归一化，不再扩写模型所选动作
  -> 原有意图校验 / HCM safety / policy / provider simulation / review
  -> 内存模拟执行 + 状态回读 + 审计 + 页面刷新
```

所有对话指令，包括歧义、无匹配和取消，都会调用 D1。设备操作始终是 HCM 能力，不是模型自行编写的 HA 服务名。开关的物理安装房间不替代灯具的逻辑服务房间。

## 安全边界

- 不把选中 UI 房间当作用户位置；优先明确房间和未过期的会话焦点。
- “它”对应多个设备、泛指多个卧室、候选集合无法完整覆盖时，不猜测、不写设备。
- 询问用法只提供只读回答选项。否定表达对应的设备不能被写入；“不要打开”不是“关闭”。这些是最小写权限限制，不是用于理解通用语言的大型规则规划器，仍有语言覆盖边界。
- 数值需要单位；检验已知 min/max/step，不允许暗中裁剪参数或把调光降级为开关。
- 仅提供已有低风险、可自动执行能力；传感器、未绑定按键和受保护能力不提供执行候选。
- 校验返回选项、完整概率分布、最高概率一致性；低分/小分差会反问。概率阈值是保守启发式，未做成功率校准。
- D1 的 confidence 是选项分数，不是执行成功概率。额外 purpose 问题不验证选中方案，不能视作独立安全证明。
- 超时、HTTP 错误、响应损坏和单槽并发冲突不执行，也不重试云端或偷偷回退本地假成功。
- 模拟 adapter 没有网络执行传输。即使真实执行环境开关开启，实验启动脚本也只允许内存设备变化。`dryRun=true` 连内存设备都不改变。

## 启动与测试

```bash
npm ci
npm run demo:d1
# 默认 D1_ENDPOINT=http://192.168.1.154:8080/v1/systemone
# 可覆盖 D1_ENDPOINT、D1_MODEL、D1_TIMEOUT_MS、PORT
```

打开 `http://localhost:5173/`。页眉显示“模拟设备”和 `D1 · d1-3b-q4`。对话栏“预览”不改变状态；“模拟执行”才改变内存设备并刷新三维房屋。原来的 HA 令牌、云端密钥均不需要。

建议顺序：打开书房射灯；查询书房射灯状态；打开书房射灯、关闭书房吊灯；打开餐厅吊灯（控制器实际在玄关）；空调调到24度；电视怎么打开（不能开机）；不要开书房灯、但打开客厅电视；卧室灯关一下（应反问主卧还是次卧）。

```bash
npm test
npm run test:adapter
npm run build
# 以下会调用真实局域网 D1，但脚本先检查 simulated=true，拒绝真实家庭环境
npm run test:d1:live
npm run test:d1:live -- --holdout
```

本分支默认测试不依赖运行中的 HA。旧 skip-planner 网络集成测试改为显式 opt-in：`HARNESS_LIVE_TESTS=1`；不要在自动调试中对真实设备运行它。

## 实测与限制

2026-10-08，局域网 `d1-3b-q4`，单推理槽、上下文 4096：

- 自动化测试 286 通过；3 个旧在线集成测试默认跳过。31 个 Adapter 测试和生产构建通过。
- 自动候选的开发回归集 22/22。最终一轮完整服务链路 P50 47ms、P95 69ms、首次请求 429ms；此前轮次 P95 约 181ms，延迟受预热和缓存影响。
- 新表达验证集首次 18/20，发现旧归一化会把“这个怎么用”的澄清覆盖为全屋清单，已修复；最终复测 19/20、P50 46ms、P95 394ms。
- 剩余失败是单设备上下文后的“关一下”：目标已收窄到书房射灯，但 D1 方案分数不足，系统反问，没有错控。没有为了通过测试而降低执行阈值或修改期待结果。

测试请求只传用户输入、会话、选择房间和 dry-run；不传测试期待的目标或答案。用例经过开发调优，因此这些数字不是独立泛化准确率。延迟只含本地服务链路，不含 STT、TTS、真实 HA 执行或重连时间，不能据此保证真实设备端到端 2 秒。

当前支持有界的开关、单数值设置、少量明确设备组合、状态/能力查询、取消/偏好不执行以及澄清。并非通用自然语言能力已经完成：电影/睡眠等开放目标、相对亮度优化、多个独立数值、复杂省略、半执行确认恢复、任意新设备操作语义、偏好自学习和语音链路尚未接入本实验。超出范围会反问，而不是使用付费模型补全。

下一步先积累真实语言的离线回放与候选覆盖测试，测量误执行率、澄清率及新增设备能力覆盖；达到质量门槛后，再接真实 HA 的只读快照做 dry-run，不直接启用写设备。
